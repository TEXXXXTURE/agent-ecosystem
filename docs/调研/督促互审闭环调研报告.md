## 一、一页结论

1. **缺口确认**：你要补的「环节三」= 督促-互审-闭环的集群级规则。现有体系已具备两块地基——§4 三段式外部评审（意见闭环雏形）+ §17/§18 记忆与两档维护（引导哲学），缺的是：**督促（谁催）、多轮互审循环（怎么转）、修订后重审（旧意见作废）、循环终止（怎么停）**。业界已有成熟零件，不需要发明，只需拼装。

2. **你的「强制 vs 自然引导」立场被业界验证**：四路调研独立收敛到同一结论——硬约束只应落在机器可判定点（校验器、CI、过滤器、接口设计），判断性协作靠模板、默认路径、事件驱动自然衔接。**STANDARDS §18 的「两档」（系统级强制 vs 约定级引导、默认约定级）不是妥协，是正确分工。** 闭环里唯一需要「强制」的，就是 NFR-02 产出物校验器这一个点。

3. **四个可直接搬的机制**（全部有已验证来源，详见第四节）：
   - **修订即重审**：GitHub「stale approval 自动作废」→ 方案一修订，旧评审意见自动标「待复核」，防旧 approve 罩新产物。这是 §4 一次性评审目前最大的窟窿。
   - **独立互审者**：Anthropic 单设 CitationAgent、GitHub 要求非作者审批；Munder 的 GOD 自裁是反例。你的 §4「无记忆外部 Agent」方向正确，缺的是把它变成循环中的常驻角色。
   - **终止条件三件套**（防循环空转）：通过信号（校验器过 = APPROVE）+ 最大轮数 + owner 人工中断点。
   - **事件驱动督促 + 轻量超时兜底**：Munder 的 Stop hook「有未读就唤醒」+ Anthropic 的「lead 自判信息充分度」证明督促不必靠定时器；但单人体系建议保留一个超时兜底（Jira 式「卡住 N 天自动升级」或 Munder 式熔断），否则 agent 卡死无人知晓。

4. **集群规则吸收**：八条可直接落地的建议（第六节 TOP 8），核心是把「压缩结论 + 指针」定为协作原子单位（MetaGPT / SWE-agent / Anthropic 三方收敛）、叶片声明加一句 handoff_description 用于路由、门禁两档分工（机器先过、Agent 审方向）、记忆触发式三桶写入。

5. **下一步**：拍板第八节清单 → 修订 soul.md / STANDARDS §4 / PRD（补闭环衔接件）→ 建契约注册表 + 首批程序化校验器 → 连起来即可用。

## 二、语境对齐：你的立场与目标场景

**你的逻辑链**（来自多轮对话）：AI PM 产品（project-pm-tracker Skill）本身可独立使用 → 给它加模块让它整块运行 → 闭环不该写成「强制行为准则」，而是各 Agent 自己连接起来就该是一个循环（**一个靠强制、一个靠本就会被引导成一套规则**）→ APM Agent 产出完整方案（选型方案 + 细节）→ 进入 coding → coding 出问题 → 需要另一个 Agent 督促完成循环 → 市面上已有方案 → 找案例 + 加自己的想法 → 集群规则吸收更多经验（自评当初写规则无规范参照，靠对模型和业务的理解自写）→ 完善后连起来即可用。

**目标闭环场景**（本报告所有映射的落点）：

```
PM/产品 Agent (project-pm-tracker)
   │ 产出完整方案（选型方案+细节）【契约：方案产出物】
   ▼
执行/编码 Agent 接手 coding
   │ 出问题 / 产出中间结果
   ▼
督促机制（事件驱动：失败信号/产出物到位即唤醒）+ 互审 Agent（独立新眼睛）
   │ 意见回填（三段式 + 严重度 + 处置追踪列）
   ▼
修订 → 复核 → 通过校验/门禁 → 流转交付；不过 → 带失败原因回炉再循环
   │ 终止条件：通过信号 + 最大轮数 + owner 中断点
```

## 四、每案例机制拆解

### 4.1 编排框架层（critic/reflect 循环怎么转）

**MetaGPT** —— 互审不靠对话来回，靠「下游角色拿上游结构化工件当下游标准」自然衔接。SOP 把流程编成提示序列，领域专长角色核对中间产物（PRD/设计/代码），意见以「下一个角色的产出」形式回填共享消息池，不是对话。核心动机是抑制 naive 链式 LLM 的幻觉级联；但它是一次性流水线，跑完即止，**没有返工闭环**——正好补你的缺口参照。映射：FR-03「契约匹配→传递」的可行性证明。

**ChatDev** —— 审是同链内的专用 reviewer 角色（设计→编码→评审→测试各阶段），`--config Human` 模式让 owner 亲自扮演 reviewer 向 programmer 提建议；评审意见直接进下一阶段对话上下文。映射：Human reviewer 模式 ≈ 你 §4「无记忆外部评审 Agent」的人在环版本；ChatChain 配置化 ≈ 契约注册表把「谁传给谁」写成声明。

**AutoGen** —— 最标准的 reflection 双代理范式：critic 是独立 AssistantAgent，系统提示词写「给建设性反馈，问题解决后回复 APPROVE」。**最值得抄的是终止条件对象化**：`TextMentionTermination("APPROVE")` = critic 说通过即停，可组合 `ExternalTermination`、`MaxMessageTermination`，另有 CancellationToken 中止。映射：APPROVE 即门禁信号，挂在 NFR-02 校验器后面；终止条件组合 = 防循环空转的工程件。

**CrewAI** —— 层级流程下自动指派 manager agent，官方原文职责是「through delegation and validation of results」做计划、派活、验收（即督促者+终审者）；任务用 `expected_output` / `output_pydantic` 的结构化输出契约定义「审到什么算合格」——这是它最接近客观标准的地方。映射：结构化输出契约 ≈ 你的产出物 schema（FR-01 校验器）。

**LangGraph** —— 循环表达最硬：critic 就是图上一个普通节点，`Command(goto=..., update={...})` 同时表达「跳回谁」和「写回什么意见」（意见作为 state 更新回填）；`recursion_limit` 硬截断、条件边收敛、checkpoint/breakpoints、`interrupt` 任意点停下等人改状态再续跑。官方还实测了「子 Agent 私有 scratchpad、只共享结果」优于共享全程思考。映射：最贴你的集成层——编排 Agent = supervisor 节点；「校验不过走条件边回炉」= NFR-02 校验断点的图化；只共享结果 = 理念「引用不镜像、不复制上下文」。

**OpenAI Agents SDK** —— 无内置 critic，审核靠 guardrails（输入/输出校验，程序化门禁而非 LLM 互评）；handoff 带 payload 一次性跳转；全程 tracing。映射：guardrails = 程序化校验器（NFR-02 固定路径）；tracing = §4「不留悬空意见」的工程化。

**本层关键结论**：① 六个框架**没有一个内置「督促者」角色**——催全部由 SOP 顺序、轮次、图边、manager 委派、handoff 自然产生，印证你的立场：督促不必写成行为准则，把产出物契约顺序排好，衔接本身就是督促。② critic 三种出身按可信度排序：程序化校验器/guardrail > 独立 critic Agent 显式互评 > 下游角色兼审。③ 闭环关键不是「怎么评」而是「怎么停」。

### 4.2 代码审核与自我验证层（意见怎么闭环、怎么审得客观）

**CodeRabbit** —— 意见闭环最完整的产品实例：评论线程逐条管理，`autofix` 直接把未解决意见自动改代码提交，`resolve` 批量标已解决，`approve` 先清空线程再通过。状态机 = 未解决 → autofix/人工改 → resolve → approve。防退化：`pause/resume/ignore` 控制噪音、增量审只看新 commit、autofix 遇 merge conflict 自动停下不硬改。映射：线程状态机直接对照 §4 处置追踪列，但它是**可执行闭环**而非人工填表。

**GitHub Copilot Code Review** —— 默认只发 Comment 评论、**不计入 required approvals**（不充当门禁，防橡皮图章）；审核力度分 Lite/Balanced 两档；每条评论带 High/Medium/Low 严重度；人对 Copilot 评论的回复它不参与多轮对话。映射：**AI 意见默认作「建议」而非「一票否决」——恰好印证你「自然引导优于强制」的立场**；严重度分级对应 §4「必须改（阻塞）/建议改（优化）」两档。

**Greptile** —— 先对全仓库建图索引（文件/函数/依赖），多 agent 并行审，评估改动对未触碰代码的跨文件影响；Draft PR 默认不审（开发期降噪）；官方自述 single-pass 不迭代。映射：审的依据应来自结构化上下文而非只看片段（对应集成层「契约注册表 + 叶片挂载」）；它没有的多轮闭环正是我们要补的。

**Self-Refine** —— 同一 LLM 既当生成器又当评论者又当修正者，论文承认「自我反馈存在天花板」，无客观终止判据、靠预设轮次停。映射：**证明 §4 为何要「不带项目上下文的外部 Agent」评审**——自审有盲区，外部新眼睛不可省。

**Reflexion** —— 环境失败信号（编译报错、任务失败）触发 agent 口头复盘，反思文本写进 episodic memory buffer，下一轮带着再试（HumanEval pass@1 从 80% 提到 91%，论文数据）。映射：把失败反思写进记忆对应 §16 交接文档 + `问题/debug-log.md` + §17 跟进日志——**记忆即迭代燃料**。

**CRITIC** —— 关键创新：自纠正必须借助外部工具（事实类用搜索、代码用解释器跑），明确论证「纯内部自我纠正会幻觉，外部反馈才是持续自改进的关键」。映射：这是 NFR-02「产出物过校验器才流转、来源锚定」的论文版背书——主观评审意见之外必须挂一个客观 verifier。

**SWE-bench** —— 完全不用主观评审：给模型真实 issue，唯一合格标准是项目自带失败测试是否转绿（FAIL_TO_PASS + PASS_TO_PASS）。终止条件客观且不可绕：测试红=没完成，测试绿=收敛。映射：把「测试/CI 即 verifier」落到集成层——主观互审（§4 三段式）与客观测试门禁分层，**主观意见可讨论，客观测试是硬门槛**。

**GitHub 人工 PR 机制** —— 状态机清晰：Request changes → 作者改 → **同一 review 人再 Approve 才解除**；`stale review dismissal` 后 push 新 commit **自动作废已有 Approve、要求重审**——防「旧审批罩着新代码」；Request changes 默认仅信息性，配了 branch protection ruleset 才真挡 merge（门禁可选挂）。映射：「stale approval 自动作废」是 §4 最该补的一环——我们现在一次性评审后方案又改，旧意见是否仍有效？

**本层关键结论**：① 客观验证与主观评审必须分层组合：收敛终点必须是客观 verifier（SWE-bench 测试转绿 / CRITIC 工具外验），主观评审只负责找问题给方向；② 防橡皮图章的核心是「改动即旧审失效」；③ 防审核疲劳靠「分级 + 聚焦 diff + 按需触发」，不是取消审核。

### 4.3 成熟产品层（任务流转、督促、门禁、防死循环）

**Munder Difflin** —— 本地代码核验（`C:\Users\A\Doubao\chats\2026-10-06\new-chat\_agent_ui_shots\` 下 README/SPEC/HIVE/ARCHITECTURE 等六份文档）。worker 完成一个 turn 后 Stop hook 触发→主进程查 inbox→有未读就回 `{"decision":"block"}` 让它继续干（**事件驱动自唤醒，不是定时器**）；GOD agent 是唯一人入口，routine 澄清自己解决，只有花钱/破坏性操作/范围变更才升级到人。消息走 FIPA-lite schema（`request/inform/propose` + `requires_reply` + `in_reply_to`），一封邮件一个 JSON 文件原子落盘，处理过移入 `.done/`。**防退化是它最强项**：三级熔断 steer→constrain→stop（loop/error storm/超预算）；消息每跳 `hops+1`，超阈值由 GOD 升级而非让两 agent 无限乒乓；stop_hook 防自杀循环；per-agent token budget；单写者目录防文件冲突。**它没有独立互审 agent**——GOD 既是编排者又是裁决者（自己人审自己人，反例）。owner 判定「靠文件传输、非原生方案、无完整范式突破」方向成立（协调层确实是文件+git+router），但熔断三级、hops cap、Stop-hook guard 三个防退化细节是工程上可直接搬的具体件。映射：GOD = soul.md 总编排 Agent；文件邮局 = 理念「产出物是最小公约数」；缺独立互审 = 正好补 §4 三段式评审的位置。

**Anthropic 多 Agent 研究系统** —— orchestrator-worker：LeadResearcher 分解问题→并行 spawn 子 agent（独立 context 窗口）→回传发现→lead 合成。督促：lead 把研究计划显式写到外部 Memory（防 context 超限丢计划），合成后自判「信息够不够」，不够就再 spawn——**没有人催、没有定时器，靠 lead 对信息充分度的判断自驱**。互审：**独立 CitationAgent** 把每个断言锚回引用位置（校验独立成专门子代理，比编排者自审不护短）；另用 LLM-as-judge 按 rubric 五维打分（事实/引用/完整/来源质量/工具效率）。意见闭环：子 agent 不传全文，产出写文件系统、只回轻量引用（「避免电话游戏」）；lead 发现缺口不是回填意见而是**直接新发一个子任务去补**。防退化：prompt 内嵌 scaling rules（简单查询 1 agent / 对比题 2-4 / 复杂题 10+）防过度投入；explicit guardrails 防 spiraling；retry + regular checkpoints 从断点 resume；同步阻塞等待子 agent 是其承认的瓶颈。映射：LeadResearcher = FR-03 编排 Agent；CitationAgent = NFR-02 来源锚定校验器的专门实例；子 agent 写文件回引用 = 理念 1 强佐证。（「较单 agent 提升 90.2%」为其内部评测自称，标一方称）

**OpenAI Codex** —— 官方无与 Anthropic 同名的多 agent 工程复盘博客，OpenAI 侧可核验的异步 agent 闭环代表是 Codex cloud agent。每个任务跑独立云端沙箱，agent 被训练成 iteratively run tests until passing（pre-commit 失败自己修、修完重试）；2025-09 后支持 schedule future work、自动 wake up 跨天继续长任务；产出附 terminal log + test output 引用作为可验证证据；合并前过 GitHub PR + required reviews，官方明说「人仍须手动 review 所有 agent 代码」；项目规则写进仓库根 AGENTS.md（agent 每次启动自动读）；沙箱默认断网防越权。映射：AGENTS.md ≈ soul.md；自动跑测试到过 = NFR-02 校验闭环的 agent 内实例；「人必须手动 review」= §4 无记忆外部评审的现实版。

**GitHub 分支保护 + Required Reviews** —— 门禁不催、硬阻断：不满足条件 merge 按钮灰，根本走不进下一步；required approvals + dismiss stale approvals + require conversation resolution before merging + required status checks + require branches up to date + do not allow bypassing（含 admin）。映射：required approvals = §4「采纳/不采纳」的工程化门禁版；**dismiss stale approvals 正好补 owner 体系目前缺口**（§4 一次性评审，方案修订后旧意见无自动作废机制）；conversation resolution = §4 处置追踪列的产品化。

**Jira SLA / Linear** —— 督促的系统级代表：SLA 计时（如 Urgent 8h / Fairly urgent 40h）、定时扫描找「due date 已过且未 Done」→自动转 `Escalated` 状态 + 通知 PM、长时间未更新（2/5/14 天）邮件提醒、breach 前可配预警；工作流状态机显式化「该谁动」。映射：**「超时自动升级」是 owner 体系完全没有的维度**——目前靠 §17「有工作才写日志」，没有「卡住 N 天自动喊人」；显式 Escalated 状态 = §6 状态机可加 `blocked/escalated`。它与 §18 默认约定级哲学不同，但可作为「自然引导循环」的最后兜底档。

**本层关键结论**：① 督促分两派——事件驱动派（Munder 唤醒、Anthropic 自判）与你 §17 哲学同向；定时扫描派（Jira）作为兜底保留；② 互审必须独立于编排者，让编排者自审自己的产出就是橡皮图章（Munder GOD 是反例）；③ 意见闭环关键不是「记意见」而是「修订后旧结论失效」。

### 5.1 闭环怎么接：契约顺序 + 校验断点 + 回炉边

把闭环画成图而不是写成人话规则（LangGraph 式图边 + MetaGPT 式顺序驱动）：

- **主机制（约定级，符合你的立场与 §17）**：事件驱动——产出物契约到位 = 下一棒被唤醒（Munder Stop hook 式「有未读就动」）；失败信号（编码出问题）= 唤醒督促/互审 Agent；Anthropic 式「信息充分度自判」由编排 Agent 承担。不设定时器、不写「每天必须汇报」。

### 5.3 互审 Agent 草案

## 七、我们的一些想法（你的立场的落地形态）

1. **「强制 vs 自然引导」的边界**：业界四路调研收敛的答案是——**强制只落在机器可判定点（校验器/CI/过滤器），判断性协作靠引导**。你的 §18 两档不是「暂时没力气做强制」的妥协，而是被验证过的正确分工。落到闭环：唯一写死的强制 = 「产出物过 NFR-02 校验器才流转」这一个点；其余（谁审、怎么回填、怎么修订、怎么复核）全部长成衔接件，Agent 走默认路径自然循环。

2. **闭环不新写一套「行为准则」**：给现有 soul.md / STANDARDS 补五个衔接件即可——契约顺序（谁传给谁）、校验断点（过不了回炉）、事件驱动唤醒（有未读就动）、修订即重审（旧意见作废）、终止条件三件套（通过信号+轮次上限+owner 中断）。连起来，循环就自己转。

3. **APM → coding → 督促的具体接法**：APM（project-pm-tracker）产出完整选型方案 → 方案以产出物契约入注册表 → 编码 Agent 收到契约即被唤醒（契约到位 = 催）→ coding 出问题（失败信号）→ 事件驱动唤醒互审 Agent 出三段式意见 → 意见带严重度回填处置追踪列 → 修订 → 复核 → 过校验器流转；修订后旧意见自动标「待重审」。整条链没有一句「必须服从」，但每一步都被上一步自然推进。

5. **循环能收敛的前提**：外部记忆（失败写进 debug-log/跟进日志，Reflexion 教训）+ 客观终止（测试/校验器转绿，SWE-bench 教训）+ 人工兜底（owner 中断点）三保险。
