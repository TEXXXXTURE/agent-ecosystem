## 一、一页结论（选型推荐速览）

1. **形态结论：混合（三明治），不是二选一。** 三路调研收敛到同一个行业共识——「判断留给 NL、兜底留给程序」。纯指令文件（AGENTS.md）程序约束几乎为零、无法测试行为；纯编排层又失去规则的可读性与跨工具可移植性。你要的是：**薄的自然语言门面 + 厚的程序约束层 + 一层衔接与测试**。

2. **自然语言层放哪（分工）**：
   - **仓库根 `AGENTS.md` = 通用门面（薄）**：6 步闭环一句话版（"方向问题升级 owner、机械问题机器兜底"）、setup/test 命令、仓库约定。放仓库根 = 跨工具标准，Codex / Claude Code / Cursor / Cline 启动自动读，零注册成本。
   - **`docs/soul.md` = 编排 Agent 深度人设（厚）**：现有 soul.md 迁移入仓并扩写 6 步闭环的完整自然语言版。AGENTS.md 用一行指向它（沿用现有「编排 Agent 接任先读 soul.md」规则）。

3. **程序约束层放哪**：
   - **`contracts/` = 契约注册表**（PRD FR-01 落点）：产出物 schema（PM 方案 / 执行 diff / 失败原因 / 决策记录）+ 校验器实现——**这是全系统唯一"强制"点**（NFR-02）。
   - **`orchestrator/` = 6 步闭环显式状态机/图**：6 步做成可编译、可测试的图与条件对象（LangGraph 式），**不写进编排 Agent 的 prompt 让它自觉**；`owner_gate` 是程序原语（interrupt 式挂起，owner 一句话 resume，0 token）。
   - **叶片声明 = 结构化注册**（PRD FR-02 落点）：NL 正文（怎么干活）+ 结构化元数据（输入/输出契约 + handoff_description + 工具白名单），形态参照 Claude Code subagents 的 frontmatter。

4. **两层怎么衔接**：NL 规则只写"方向和判断"，凡涉及"过不过/停不停/升级不升级"全部指向程序实体（schema、校验器、门、终止条件对象）；程序层反向校验 NL 声明（CI 里 lint：AGENTS.md 存在、soul.md 引用的文件存在、字节预算告警）。

5. **规则怎么测试（可执行，回答"工程可实现可测试"）**：确定性测试为主——schema 校验器单测、6 步闭环状态机终态断言（喂假事件流断言状态迁移）、两档分流断言（机械型→自解路径 / 方向型→owner_gate 路径）、终止条件单测（喂假消息断言 should_stop）；规则文件 lint 进 CI；LLM-judge 小样本 eval（promptfoo/DeepEval 式）作为渐进第二档。

6. **对你已拍板 6 步闭环的直接含义**：闭环的正确形态不是"写一套规则让 Agent 自觉遵守"，而是**显式图 + 机器闸门**——PM 产出→schema 校验（免费）→owner_gate（0 token）→执行→两档分流（程序判定）→校验回环。强制只落在 schema/校验器/图边上，其余（怎么审、怎么修订）仍走 NL 引导。

## 二、语境：已拍板的 6 步闭环（形态设计的目标约束）

```
① PM 产出方案 + 机器 schema 校验（免费）
② owner 审方案拍板（人在环，一句话定方向，0 token）——替代"方案互审循环"
③ 编码执行（N 次调用，必须）
④ 出问题分两档：机械问题 → 编码 Agent 自解 + 机器校验兜底；方向问题 → 直接升级 owner 一句话定夺（0 token）——替代"编码互审循环"
⑤ 机器校验（测试/schema）过 → 交付；失败 → 带原因回③
⑥ 可选：关键产出物（方案/交接文档）一次互审 + 落痕（0-1 次调用）
核心规则一句话："方向问题升级 owner、机械问题机器兜底"
```

本报告所有形态建议以能承载这 6 步为准。

## 四、形态选型对比（针对你的场景）

| 对比维度 | 纯指令文件（AGENTS.md/soul.md） | 纯编排层（代码/schema/图） | **混合（推荐）** |
|---|---|---|---|
| 可测试性 | 差（无官方校验器，行为靠 LLM 自觉） | 强（图/schema/条件对象可单测） | 强（确定性部分全可测 + 规则文件 lint） |

| 单 owner 维护成本 | 低（一个文件改起来快） | 中（改代码要测） | 中（分层后各自小，改动有回归测试兜底） |

| 与 6 步闭环契合 | 弱（两档分流/回环写 NL 不可测） | 强（显式图+闸门） | **强**（闭环=图，规则=NL 门面） |

**推荐：混合三明治**——`AGENTS.md`（薄 NL 门面）→ `soul.md`（厚 NL 人设）→ `contracts/ + orchestrator/`（程序约束与图）→ `tests/`（规则有效性测试）。

## 五、推荐方案（具体落点）

### 5.1 自然语言层放哪

| 文件 | 定位 | 内容（形态示例） |
|---|---|---|
| 仓库根 `AGENTS.md` | 通用门面（薄，给所有 Agent 与人类看） | ① 仓库怎么跑：`pnpm install / pnpm test`（照抄 Codex/AGENTS.md 规范写法）；② 代码约定；③ **6 步闭环一句话版**：`## 协作闭环：方向问题升级 owner、机械问题机器兜底`——用 6-10 行写清六步与两档分流原则；④ 一行指向 `docs/soul.md` |
| `docs/soul.md` | 编排 Agent 深度人设（厚，现有 soul.md 迁移+扩展） | 现有五节（身份/形象/决策规则/价值导向/禁区）+ 新增「六、6 步闭环执行细则」：每步的 NL 规则、两档分流的判断启发式、owner_gate 何时触发、互审与落痕怎么走 |
| `docs/PRD.md` | 产品文档（从 vault 迁移完整 PRD 原件，STANDARDS §11） | 含 FR/NFR；新增 FR-07「规则形态」或并入现有条款（拍板后定） |

**分工原则**：AGENTS.md 写"凡机器能判的交给机器"；soul.md 写"机器判不了时你怎么判断"。两处不重复，AGENTS.md 引用 soul.md。

### 5.2 程序约束层放哪

| 目录 | 内容 | 对应条款 |
|---|---|---|
| `contracts/schemas/` | 产出物 schema（Pydantic 或 JSON Schema）：`pm_plan`（PM 方案）、`exec_diff`（执行 diff）、`failure_reason`（失败原因，带结构化原因字段供回流）、`decision_record`（决策记录，已有练手） | PRD FR-01 |
| `contracts/validators/` | 校验器实现（机器强制点、免费、0 token）——schema 校验 + 来源锚定；校验失败抛可捕获异常 | PRD NFR-02 |
| `contracts/registry.*` | 叶片能力声明：每个叶片一行「输入契约 / 输出契约 / handoff_description（我擅长什么、何时该选我、何时别选我）/ 指针」 | PRD FR-02 |
| `orchestrator/closure.py` | **6 步闭环显式状态机/图**：节点 = PM产出→schema校验→owner_gate→执行→两档分流→校验回环；边 = 显式拓扑（LangGraph 式或自研轻量状态机，技术选型待拍板） | PRD FR-03 |
| `orchestrator/termination.py` | 两档判定与终止条件对象（AutoGen 式组合）：`SchemaValidationPassed \| NeedsOwnerDecision \| MaxRetryExceeded`；机械型失败→回③自解；方向型→owner_gate | 防循环空转 |
| `orchestrator/gates.py` | `owner_gate`（interrupt 式人环原语）：程序挂起等 owner 一句话 `resume(decide)`，0 token | 6 步②④ |
| `leaves/` | 工具叶片指针清单（引用不镜像，迁移工具叶片清单） | 挂载规则 |

**叶片声明的形态建议**（参照 Claude Code subagents 混合文件）：每叶片一个 Markdown：frontmatter 写结构化元数据（`name` / `description` 路由描述 / `input_contract` / `output_contract` / `tools` 白名单），正文写"怎么干活"的 NL。程序按 frontmatter 发现、路由、注入；frontmatter 解析失败即拒载并记日志。

### 5.3 两层怎么衔接

1. **NL → 程序（下行）**：AGENTS.md / soul.md 里凡涉"过不过/停不停/升级不升级"的表述，一律写成**指向程序实体的引用**（例：`PM 方案必须通过 contracts/schemas/pm_plan 的校验（validators/schema_validator.py）才进 owner_gate`）——不是让 LLM 自觉，是指向机器闸门。
2. **程序 → NL（上行）**：契约注册表与图里可挂 `rationale` 字段回指规则条款（如"此分支对应 soul.md 六·④ 两档分流"），让图可审计、可解释（soul.md 规则三"可解释优先"）。
3. **规则文件 lint（衔接的验证）**：CI 脚本检查——AGENTS.md 存在；soul.md/AGENTS.md 引用的文件与 schema 路径真实存在（lint-agents-md 式断言）；若有 frontmatter 则 schema 校验（仿 `claude plugin validate`）；字节预算告警（仿 Codex 32KiB 教训）。

### 5.4 规则怎么被 Agent 使用（加载路径）

```
Agent（任意工具：Codex/Claude/Cursor/Cline）
  ├─ 自动读仓库根 AGENTS.md（跨工具标准，零注册）→ 拿到 6 步闭环一句话 + 命令 + 指向
  │
  └─ 编排 Agent 启动（现有机制扩展）
       ├─ 先读 docs/soul.md（新会话/新 Agent 接任必读，现有规则）→ 深度人设与 6 步细则
       ├─ 编排代码 import contracts/ + orchestrator/（schema、图、门、终止条件）→ 程序强制
       └─ 叶片按 registry frontmatter 发现与路由 → 注入 NL 正文 + 工具白名单
```

**关键点**：AGENTS.md 的加载是工具自动的（0 成本）；soul.md 的加载靠"接任先读"规则（现有约定级机制）；程序层的加载是 import（编译期强）。

### 5.5 规则怎么测试（可执行验证思路）

**第一档（确定性，第一版就做，进 CI）**：
| 测试 | 方法 | 依据 |
|---|---|---|
| schema 校验器单测 | golden cases：合法方案/缺字段/类型错/来源锚定缺失 → 断言通过/拒绝 | CrewAI output_pydantic / OpenAI output_type 范式 |
| 6 步闭环状态机测试 | 喂假事件流断言状态迁移：PM 产出→校验→owner_gate→执行→两档→回环/交付 | LangGraph 图编译 + checkpointer 重放 |
| 两档分流断言（**终态断言**） | 机械型失败（测试红/schema 错）→ 断言走自解路径；方向型（需求歧义/范围变更）→ 断言走到 owner_gate | Anthropic 终态评估方法论 |
| 终止条件单测 | 喂假消息断言 `should_stop`（SchemaPassed / NeedsOwner / MaxRetryExceeded） | AutoGen TerminationCondition 单测 |
| 规则文件 lint | AGENTS.md 存在、引用断裂、frontmatter 合法、字节预算 | lint-agents-md / claude plugin validate 思路 |

**第二档（渐进，可选）**：小样本 LLM-judge——用 promptfoo（`promptfooconfig.yaml`：确定性断言 + `llm-rubric`）或 DeepEval（pytest 风格 + threshold）把"两档分流是否正确"做成 golden 输入集（方向型/机械型各若干条），进 CI 当 pytest 跑；Anthropic 经验：20 条 query 小样本起步，不攒大 eval。

### 5.6 6 步闭环在两层里的落点（已拍板闭环 → 形态映射）

| 6 步 | NL 层怎么写（AGENTS.md/soul.md） | 程序层怎么做（contracts/orchestrator） |
|---|---|---|
| ① PM 产出 + schema 校验（免费） | "PM 方案必须过 schema 才上报" | `pm_plan` schema + validator（免费=无 LLM 调用） |
| ② owner 一句话拍板（0 token） | "方案不经 owner 拍板不进执行；不做方案互审循环" | `owner_gate` 节点（interrupt 挂起，resume 即续） |
| ③ 编码执行（N 次） | 执行叶片声明：接契约即开工 | 执行节点（叶片注册后进图） |
| ④ 两档分流 | 核心句：**方向问题升级 owner、机械问题机器兜底** | 分流判定（程序）：机械=机器可检测（测试/schema/exit code）→自解+机器兜底；方向=其余 → owner_gate |
| ⑤ 校验过交付/失败回③ | "失败必须带原因回流" | 校验器 + 回环边；`failure_reason` schema 化（失败写记忆，Reflexion 式） |
| ⑥ 可选互审 + 落痕 | 复用 §4 三段式（一句话结论+四问+处置追踪列） | 可选节点 + 落痕写 registry/记忆（0-1 次调用） |
