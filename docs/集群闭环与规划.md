## 一、这个集群是什么

**一句话**：Agent 生态**集成层**——把平级的能力单元（工具 / Agent / 项目）组织为可组合总系统的集群规则 + 产出物契约 + 6 步协作闭环。

所有能力单元平级：只通过**产出物**交流（输入契约 → 输出契约），不互相依赖、不融合程序。本项目只负责"组起来"。

**三件套**

| 件 | 职责 | 落点 |
|---|---|---|
| 编排 Agent | 意图路由 → 任务分解 → 契约匹配 → 传递 → 校验 → 循环 | `orchestrator/` |
| 契约注册表 | 规则本体：产出物 schema + 校验器 + handoff 边 | `contracts/` |
| 叶片挂载 | 工具以"引用"接入，只存指针不镜像内容 | `leaves/` |

**核心规则一句话**：**方向问题升级 owner、机械问题机器兜底。**
**规则形态**：混合三明治——判断留给自然语言（`AGENTS.md` / `soul.md`），兜底留给程序（`contracts/` + `orchestrator/`）。

## 二、6 步协作闭环

```
① PM 产出方案 + 机器 schema 校验（免费）
② owner 审方案拍板（0 token，人在环）
③ 编码执行（Coding Agent，N 次调用）
④ 出问题分两档：机械 → 自解 + 机器兜底；方向 → 直接升级 owner（0 token）
⑤ 机器校验过 → 交付；失败 → 带原因回 ③
⑥ 可选：关键产出物一次互审 + 落痕（0-1 次调用）
```

| 步 | 动作 | 成本 | 状态 |
|---|---|---|---|
| ① | PM 产出方案 + `pm_plan` schema 校验 | 免费（机器） | ✅ |
| ② | owner 拍板（owner_gate，写 decision_record） | 0 token（人） | ✅ |
| ③ | 编码执行（叶片按 registry 接契约） | N 次 | ✅（叶片在跑，链路未串） |
| ④ | 两档分流（`termination.py`） | 机器 + 0 token | ✅ |
| ⑤ | 交付校验（`exec_diff`）+ 失败回流 | 机器 | ✅ |
| ⑥ | 可选互审 + 落痕 | 0-1 次 | 🔧（规则有，实体待建 R3） |

**状态机落点**：`orchestrator/closure.py`
`PLANNING → SCHEMA_CHECK → OWNER_GATE → EXECUTING → DIAGNOSIS → VERIFY → (DONE | 回 EXECUTING)`

## 三、循环与人机边界（设计说明）

**循环有两个，都是机器驱动，不是 Agent 互审：**

- **回路①（⑤→③）**：交付前 `exec_diff` 过不了 schema → 带 `failure_reason`（结构化原因 + 现场摘要）回流重做。
- **回路②（④→③）**：执行异常 / blocked → 两档分流，机械问题自解后回 ③。
- **封顶**：终止条件三件套——`schema_passed`（成功）/ `needs_owner`（升级）/ `max_retry`（超限 → FAILED，防空转）。

**人被放在两个闸门，只"说话"不烧 token**：② 方案拍板、④ 方向问题升级。

**两档分流判定**（`classify_failure`）：
- 机械（可机器检测）：`test_failed` / `schema_invalid` / `exit_nonzero` / `param_missing` → 自解
- 其余一律 → 方向问题 → 升级 owner（安全默认）

**为什么不做"Agent 互审 Agent"的每轮循环**：token 成本。owner 一句话不烧 token，且比任何互审 Agent 都清楚要什么。业界佐证：MetaGPT / ChatDev / AutoGen / CrewAI / LangGraph / OpenAI SDK 六个框架**没有一个内置"督促者"角色**——催由契约顺序、图边、handoff 自然产生。

**唯一该写死强制的，是产出物校验器。**

## 四、契约（规则本体，首批 4 个 schema）

| schema | 产出物 | 流转节点 |
|---|---|---|
| `pm_plan` | PM 方案 | ①→②（过校验才进 owner_gate） |
| `exec_diff` | 执行 diff | ③→⑤（交付前校验） |
| `failure_reason` | 失败原因（结构化，带回流） | ⑤→③ |
| `decision_record` | 决策记录（owner 拍板留痕） | ② |

**校验器 = 全系统唯一强制点**（`contracts/validators/schema_validator.py`）。
**契约变更流程**：先记 ADR → 改 schema + 升 `schema_version` → 同步校验器测试 / README / 叶片 frontmatter → 兼容期后删旧版。

## 六、集群规划（三环节）

用户的原始拆解 → 落地：

| 环节 | 内容 | 现状 |
|---|---|---|
| 1. AI PM 职能 | 产品需求部分全部功能，可加工具扩展 | ✅ `project-pm-tracker` |
| 2. 项目管理职能 | GitHub 交接协议（REQUIREMENTS / 交接文档 / 状态记录为权威源） | ✅ project-vault 规则 |
| 3. 督促 / 互审闭环 | Agent 互相审核作业、提意见、形成循环 | ❌ **唯一缺失的一块** |

**一个关键立场**：闭环不是写成强制行为准则，而是**让各 Agent 自己连接起来就形成循环**——不靠强制，靠契约顺序与交接自然涌现。
